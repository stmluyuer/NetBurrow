# Hook 出站队列的后续优化空间

更新：2026-09-15。

## 当前决定

默认实现舍弃“空队列原子标志”和“每位玩家用量表”，需要时直接检查、遍历真实队列。保留互斥锁、容量限制、同对端发送顺序、公平调度、缓冲发送条件和游戏实例隔离。

这两项属于性能优化，不是联机必需功能。撤掉它们是为了减少额外状态和排查变量，**尚未证明它们导致了游戏的 0xc0000409 闪退，也未证明撤掉后已经解决闪退**。

## 两项机制与预期收益

| 机制 | 原先作用 | 当前替代方式 | 可能有收益的场景 |
| --- | --- | --- | --- |
| 空队列原子标志 | 用额外的 `pending` 标志表示队列是否有待发包；无包时跳过加锁检查 | 每次在互斥锁保护下检查真实队列 | 高频空闲轮询，且锁竞争或空轮询 CPU 开销已被测量为瓶颈 |
| 每位玩家用量表 | 缓存每个对端的待发包数、字节数及立即发送包数，供容量检查、缓冲发送和会话状态查询使用 | 遍历真实队列计算；诊断需要时生成临时快照 | 队列经常积压，且重复统计占据可观 CPU 时间或延长游戏线程等待 |

原子标志不是互斥锁。删除该标志不等于删除并发保护；删除用量表也不等于删除玩家额度或缓冲发送规则。

## 性能判断及证据边界

此前问题日志的部分采样中，出站队列通常只有 0～1 个包。对这样的正常负载，遍历成本预计较小，用量表收益有限；采样不代表所有瞬时峰值，也不能代表长期高积压场景。

目前没有两种实现的性能基准数据，不能给出提升百分比，不能声称所有场景差异都很小。已通过的功能、并发和积压恢复测试不等于性能基准，也不等于真实游戏不再闪退。

## 何时重新考虑

只有测量证明队列检查或统计是实际瓶颈时，再考虑恢复优化：

1. 固定同一源码基线、工具链、构建方式和测试负载，一次只启用一项机制。发送锁策略、回调处理和网络配置应保持一致。
2. 同时覆盖空闲轮询、正常四人流量、突发流量、积压和单人占据大部分流量。分别记录 CPU 开销、锁等待、发送调用耗时的中位数及高分位数、吞吐量、队列深度和拒绝原因。
3. 在有代表性的真实对局中复核收益与卡顿，避免仅用高积压压测为正常对局的优化收益背书。
4. 收益不明显时，继续保留直接检查、遍历队列的实现，不为优化而增加状态同步负担。

## 重新实现的约束

- 空队列标志只能作为提示，真实队列是状态依据。必须验证入队发布、出队、清空、缓冲包尚未满足发送条件以及线程唤醒之间的交错，避免有包却长期不再处理。
- 用量表如需恢复，入队、出队、关闭频道、成员离开、故障清理、换游戏实例和停止时必须同步维护。用真实队列重新计算的结果做一致性断言，不能仅将缺失表项或 `unwrap()` 改成默认值来掩盖失配。
- 保留容量、顺序、公平调度和实例隔离；不得为性能收益扩大到无界缓存、错误回退或默默丢弃可靠数据。
- 锁内不得执行网络收发、日志磁盘写入或游戏回调；锁策略的变化须独立评估游戏线程等待和死锁风险。

## 已有对照分支

- `codex/ab-without-queue-optimizations`：`12363c4`，舍弃两项机制，作为当前默认队列实现的来源。
- `codex/ab-keep-queue-optimizations`：`d53ec53`，保留两项机制。

上述 A/B 基线均包含后来调整的发送等待锁和移除合成回调，**不是历史 0.1.13 与原始 0.1.14 的完整对照**，也不能用它们独立判断锁策略是否导致闪退。重新评估时应从当时的最新共同基线建立对照，避免混入其他版本差异。
