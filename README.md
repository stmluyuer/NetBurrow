# NetBurrow

NetBurrow 是给《以撒的结合：忏悔+》朋友联机使用的 Windows 工具。它把已启用的游戏 P2P 数据定向转发到同组成员；Relay 只保留在线连接和当前游戏实例，不保存房间历史。

最近修复了什么、更新时需要注意什么，请看[更新日志](CHANGELOG.md)。

当前开发版的游戏内接入采用 [TractorBeam 的 Windows Hook 策略](https://github.com/mcthesw/TractorBeam/blob/ea0393f5665dd1e0775d9dc1d0c987304461191c/crates/native-hook/src/windows/steam.rs)：拦截接口创建与 Steam 回调，只替换收发入口并观察原生会话状态；会话接受、关闭和状态结果由 Steam 处理。收发采用替代模式，数据只通过 NetBurrow，不混用原生 Steam 数据通路；同组朋友都应启用工具。Hook 内发送立即按入队顺序处理，接收按频道先进先出；入口被还原后会在回调中重新接管。

本次保留 NetBurrow 的注入初始化、组码、IPC/Relay 协议、成员与游戏实例校验、可靠队列上限及短断恢复，因此无需为这次策略调整更新 Relay。实际收发队列不是逐行复制参考实现，仍保留查询后数据包被清除时要求重新查包的保护。此改动尚未证明原有偶发闪退已消失，需退出游戏并使用完整新包验证真实联机。

## 使用前准备

先让服务器端 AI 按 [服务器部署说明](docs/server-ai-handoff.md) 构建并启动 Relay。客户端填写的服务器格式是 `主机名或IP:端口`，默认端口为 `24872`，TCP 和 UDP 使用同一个端口。

解压 `NetBurrow-<版本>-win-x64.zip` 到固定目录，不要单独移动其中的 `NetBurrow.exe`、`netburrow-injector.exe` 或 `netburrow_hook.dll`。从 0.2.1 起，客户端 ZIP 只包含这三个文件；闪退采集脚本已内置，文档和手动采集入口仅保留在源码仓库。首次运行时会在 `%LOCALAPPDATA%\NetBurrow\settings.json` 保存本机设置；压缩包不会包含该文件。

## 连接步骤

“启用联机”会先在后台自检配置、32 位游戏与工具文件，再用现有协议短暂连接 Relay 检查握手与成员状态支持；通过后才启用。也可单独点击“启用前自检”。自检不启动游戏或加载 Hook；游戏文件版本会显示，但没有版本白名单，兼容性仍需实际接入确认。检查期间修改连接设置后需重新检查。

1. 打开 `NetBurrow.exe`，填写 Relay 地址。在“游戏与传输设置”中确认游戏路径是实际的 `isaac-ng.exe`。
2. 点击“创建联机组”创建 `NB1-` 开头的组码，私下发给同一局的朋友；朋友在自己的工具中粘贴同一个组码。
3. 默认选择 TCP。两端和 Relay 都确认可用后，可改为“UDP 优先”：不可靠游戏包走 UDP，可靠包仍走 TCP。
4. 点击“启用联机”，状态显示“Relay 已连接，请从 Steam 正常启动游戏”后，从 Steam 正常启动游戏并使用原有邀请、开局流程。

启动游戏前工具可以长期等待。游戏关闭后会回到等待状态；重新启动游戏会使用新的实例代号。默认关闭窗口会退出工具并停止联机；开启“关闭窗口时最小化”后，关闭窗口会正常最小化到任务栏，联机继续。该选项切换后自动保存，不会保存尚未确认的连接设置；保存失败会恢复原值。托盘可显示窗口、停止联机或退出。重复启动工具会唤回现有窗口。

连接异常会显示对应处理步骤，并提供“查看排查日志”入口；服务器不可达、连接超时、满员、拒绝加入和协议不匹配分别提示。游戏接入失败会提示检查文件或版本并重开游戏。同组看不到朋友时，请核对双方服务器地址和完整组码；不同的有效组码会进入不同联机组。

- 连接设置会标记“未保存”和“尚未应用”；联机期间可展开查看本次实际使用的配置，保存新设置不会改变当前会话。
- “最近使用的连接”保留最多 5 条服务器与联机组记录，仅存本机。选择记录只填入表单；移除记录不影响当前填写或正在使用的连接。
- 联机质量反映到 Relay 的延迟与心跳：延迟 ≥150 ms、最近 20 个样本极差 ≥80 ms，或最近 60 秒发生断线时提示波动；延迟 ≥300 ms 或 5 秒未收到心跳提示异常。它不是玩家间延迟或丢包率，也不影响现有发送频率和联机协议。
- “启动设置”中的开机启动与启动后最小化独立控制，默认均关闭。开机启动只在用户打开开关时设置当前账户的 Windows 登录启动项，不会自动启用联机；移动工具后需重新开关一次更新路径。

- “导出诊断”生成本机 UTF-8 文本文件，包含版本、状态、计数和每份日志末尾最多 128 KiB；隐藏组码、长标识符及已知显示名等内容，省略疑似凭据和包含本机路径的日志行。文件位于 `%LOCALAPPDATA%\NetBurrow\diagnostics`，可在界面定位，不会自动上传。
- 正常退出时记住窗口位置、大小和最大化状态，下次启动恢复；最小化退出后仍以正常或最大化窗口打开。原显示器移除导致位置完全离屏时，由 Windows 调整到可见位置。
- “关于”页提供“自动检测更新”开关，默认关闭，旧配置也默认关闭。开启时检查一次，以后每次启动在后台检查一次，不定时轮询、不弹窗、不影响联机；开关自动保存，关闭后不再发起自动检查，已经开始的请求允许完成。随时可手动点击“检查更新”；发现新版时，首页显示“查看更新”，关于页显示中文说明，并通过“下载新版 ZIP”在浏览器下载完整包。检查失败时可重试或手动访问发布页，不代表已是最新版。下载后先退出游戏和 NetBurrow，将完整包解压到新文件夹并启动新版，本机设置会保留。软件不自动安装或替换文件。
- “重要状态通知”默认开启，切换后自动保存。接入成功、连接中断或接入失败时发出静音托盘通知，点击通知可打开工具；成功和异常通知各自 30 秒内不重复，关闭通知不会在重新开启后补发旧状态。通知显示仍由 Windows 通知设置控制。

如果游戏已经启动，可在“游戏与传输设置”勾选“允许中途 Hook（实验性）”，然后点击“启用联机”。该设置默认关闭，会随配置保存；启用联机期间不能修改。请仅在主菜单、尚未联机时使用：工具不能识别主菜单或阻止对局中接入，也不能迁移已经建立的原生数据通路。失败或断线后仍须重启游戏，不能靠反复启用工具恢复当前进程。

## 同组成员状态

启用联机后，状态卡会显示同组所有成员的显示名、游戏状态、到 Relay 的延迟、实际 TCP/UDP 状态和累计收发包数。可在“游戏与传输设置”填写可选显示名，最多 24 个字符；不填写则显示成员编号。

延迟是各成员自行测得的“该成员 ↔ Relay”往返时间，不是玩家之间的端到端延迟。状态约每 3 秒上报一次；超过 10 秒未更新会标记过期并隐藏旧统计。数据只在当前组内共享，未上报的成员显示“待上报”。

使用本次成员状态功能前，先按 [服务器部署说明](docs/server-ai-handoff.md) 从 GitHub 的指定分支和固定 commit 更新 Relay，再让所有朋友更新客户端。新版客户端连接不支持状态同步的旧 Relay 时，会在接入游戏前提示更新服务器。新版 Relay 仍接受旧客户端，但旧客户端不能上报或查看这些统计。服务器更新会断开当前连接，请在一局结束后操作，并重启游戏再开始新局。

## 注意事项

- 本版只接受 32 位的 `isaac-ng.exe`；默认只接入启用工具后启动的游戏，允许中途 Hook 后也会尝试接入已运行的唯一匹配进程。
- 组码相当于当前 Relay 的组凭据，不要公开发布或发给不在本局的人。它不是 Steam 账号认证，也没有 TLS 加密。
- 遇到“正在恢复”时暂时保留游戏，等待原会话重接。恢复失败、主动停止联机或工具异常退出后，请完全退出并重启 `isaac-ng.exe`，再开始新的对局；不承诺热卸载 Hook DLL。
- 本次尚未完成 Linux 实机构建或两台机器的真实游戏对局验证。客户端启动检查通过；本次成员列表截图为黑屏，实际布局和托盘人工操作仍需确认。
- Steam 始终负责回调注册和派发，Hook 不调用游戏持有的回调对象，也不合成会话状态；游戏实际联机行为仍需实机确认。

## 日志排查

启用联机后，`network.log` 每约 1 秒记录 Relay 心跳距今时间、延迟、恢复次数、队友探测和游戏收发计数；网卡连接状态在变化时及每 30 秒记录一次。采样在独立线程运行，不新增外网探测。日志同时记录实际采样间隔与单调计时，便于识别电脑休眠、调度停顿或系统时钟调整；Relay 延迟回复和连接中断另记事件。网卡只记录本机接口编号与状态，不记录 IP、MAC、Wi-Fi 名称、Steam 身份或数据包内容。

网络日志最多保留当前和上一份各 8 MiB；导出日志包包含网络日志以及客户端、Hook、注入器的轮换日志，避免延迟导出时漏掉事发前记录。异常采集也保存网络日志。队友探测仍为每 5 秒一次，游戏计数来自最近的 Hook 报告；这些记录不能保证捕捉所有不足 1 秒的断网，也不能单独证明 Steam 大厅在线或判定退房原因。

### 客户端卡顿容错（A）

客户端与 Hook 必须使用同一完整包。新版本在绑定游戏前确认本地 IPC 能力；混用旧 Hook 会提示更新并重开游戏，不需要为这次客户端改动更新 Relay（服务器应保留成员离开的连带断线修复）。

运行中用已验证游戏进程的固定句柄确认退出；查询失败不再直接当成游戏退出。IPC 收发使用独立、有界队列，6 秒响应慢显示警告，运行中读/写截止统一为 30 秒；确认退出、连接被关闭或协议错误仍立即处理。可靠队列超限会明确隔离受影响成员，其他成员与 Relay 不因此整体停止；不会静默丢弃可靠数据后继续显示正常。

本地测试覆盖 20 秒不读取游戏数据后恢复、集中流量积压与半帧收发。缓冲有包数和字节上限，不保证任意带宽下均能停顿 20 秒。IPC 和 Relay 真断后的恢复条件见下节；游戏房主迁移不在范围内。工具在线不等于游戏对局已恢复，四人真实对局仍需实测。

### 原会话短断恢复

新版 Relay 与客户端协商成功后，意外断线会保留原成员和游戏绑定，最长尝试恢复约 120 秒。Hook 与客户端仍存活时，本地 IPC 中断约 3 秒内也会尝试恢复同一游戏实例，无需重复注入。诊断页和导出显示 Relay 恢复状态、Relay/IPC 成功恢复次数。

Relay 拒绝一次恢复请求不会立即停止游戏接入，客户端会在上述 120 秒预算内继续尝试。新版 Relay 确认旧会话已不存在并明确允许重新加入时，客户端重新通过组白名单校验，再用原 Hook 的游戏身份和实例代号绑定新会话，无需重开游戏。重新加入会丢弃旧 Relay 会话的队列与未确认重放记录，避免把可能已送达的数据重复投递；它不保证当前对局无损续接。仅恢复原会话时才保留可靠数据重放。旧 Relay 未明确允许时只重试原会话。

可靠数据和身份切换消息使用确认水位及有界重放，收到重复记录时不重复投递。确认只表示下一传输阶段接纳，不表示游戏已经读取或推进。每方向最多保留 4096 帧、8 MiB 未确认记录，Relay 还受原有单连接和全局字节预算限制；额度耗尽时明确失败。恢复期间不积攒新的不可靠包和非必要探测。公网重接后，本次启用保持 TCP 传输，下次重新启用才重新尝试 UDP。

这项功能要求更新 Relay，并完整更新客户端、helper 和 Hook（IPC 能力值 7）。不支持恢复协商的旧 Relay 可按原通信方式工作。服务器重启或会话过期会丢失原会话；是否可重新加入取决于服务端的明确许可及重新鉴权。仍存在的会话身份不符或状态无效时不会获得重新加入许可。主动停止或游戏进程退出后不续用原游戏。网络通路恢复不能保证游戏自身继续同步，尤其画面卡住但连接持续正常的情况；此时仍需记录卡住现场。

诊断包含 Hook 实际发送/读取调用、丢弃与拒绝、锁忙、队列积压和入口变化。当前策略会检查已登记接口并重新接管被改回的收发入口，`hook.log` 的 `interface_repairs` 记录补装次数；补装成功不显示接入失败。无法安全安装或恢复时停止接入，不重复注入 DLL。

Hook 内数据按入队顺序发送、按频道先进先出读取；客户端与 Relay 仍按成员调度，同一成员的消息顺序和频道保持，控制消息不跨越游戏实例切换屏障。单成员超限优先处理该成员的积压，不再无差别清空其他成员的不可靠包；全局容量不足时仍可能按规则丢弃必要的不可靠数据。

“导出诊断”和客户端每 10 秒日志现在分成员列出 Hook 发送调用/拒绝、入站接收、游戏实际取走、丢弃、入站失败清理、收发队列和最老等待时间。`member` 是本次 Relay 临时编号，不是 SteamID；计数限定当前游戏实例，重开后重置。外层锁忙仍只计在全局统计，不能从分成员发送数推算所有原始游戏调用。新增摘要要求成套重建客户端和 Hook，旧能力包不能混用；公网协议不变。

画面不推进但信号格仍更新时，在“诊断”页点击“记录卡住现场”，保存带时间标记的当前状态及近期日志，再记录其他玩家是否同样停住。Hook 的 `game diagnostics` 每约 10 秒输出按成员、通道和发送类型划分的累计包数、字节数、最后收发/取包距今时间，以及重新绑定和队列清理原因；`game api` 记录查询、读取、原生会话状态查询、入口补装和读取截断。接受与关闭接口完全交给 Steam，不再采集这两类调用。细分流计数在本次 Hook 生命周期内累计，成员重新绑定不清零，需结合事件判断边界。统计有容量上限，省略时会报告计数。现场记录不自动判定死锁，也不重连或重置对局；持续收发和低延迟不能证明游戏同步正在推进。Hook 细分日志本身无需修改 Relay，运行中的旧 Hook 需退出游戏后使用新构建重新接入。

“诊断 → 队友路径与数据序号”另提供两项需要新版客户端和 Relay 配合的诊断，现场导出及每约 10 秒的客户端日志也包含相同统计：

- **数据包序号**：客户端收到 Hook 数据后、网络发送入队前，为每位目标成员的可靠/不可靠流分别编号；类型 2/3 共用可靠流，跨通道保留原顺序。对端客户端在入站队列出队后统计跳号、乱序、重复及最近 256 个序号内的缺号。`assigned` 不表示实际发送完成；`gaps_detected` 是累计跳号，迟到补齐不回减，当前窗口看 `missing_window`。窗口之外只统计 `too_old`，不能准确区分迟到与重复；没有后续数据时无法单凭序号识别末尾缺包。序号元数据增加 16 字节，接近 UDP 上限的包可能按原有规则改走 TCP；元数据在送给 Hook 前移除，不改变游戏载荷；诊断序号本身不触发重传或去重，短断恢复另用独立的会话记录处理。
- **队友往返探测**：已绑定游戏的双方每约 5 秒通过 TCP 执行“本机客户端 → Relay → 队友客户端 → Relay → 本机客户端”，5 秒未回复记超时，显示最近成功 RTT 和距今时间。它覆盖可靠数据的网络通路，不经过游戏 Hook，也不证明 UDP 或游戏同步正常。客户端每轮最多发 4 个请求、最多跟踪 32 位成员，Relay 每个来源每秒最多转发 32 个请求/回复，超量探测丢弃。成员、游戏实例或 Relay 连接变化后重置相关统计。

兼容协商使用保留的 `Ping(0x4e42444941470001)`；新版 Relay 只向主动协商的客户端发送诊断成员快照，只有双方均支持时才启用新数据帧和队友探测。旧客户端可继续使用新版 Relay；新版客户端连接旧 Relay 时保留原通信并显示未确认诊断支持，不把未支持记成丢包或探测超时。完整启用两项诊断需要更新 Relay 和所有参与排查的客户端。

点击“查看日志 → 打开日志文件夹”，或直接打开 `%LOCALAPPDATA%\NetBurrow\logs`。

偶发闪退可在“日志与诊断”开启“自动记录闪退”：首次确认本机采集说明和微软 ProcDump 许可，之后启用联机便会后台跟随游戏启动、退出和重开。界面显示监视状态；异常发生后自动收集完整内存和前后日志，并生成排查 ZIP，点击“打开排查包”即可找到。原始记录保存在 `%LOCALAPPDATA%\NetBurrow\crashes`。完整步骤、手动脚本用法和采集限制见 [闪退采集说明](docs/crash-capture.md)。

要一起发送排查材料，可在“日志与诊断”点击“一键打包日志”：后台将当前 `client.log`、`injector.log`、`hook.log`、新生成的 `diagnostics.txt` 和最近一次完整崩溃记录压缩为一个 ZIP，保存到 `%LOCALAPPDATA%\NetBurrow\diagnostics`。手动打包完成后会打开资源管理器，自动采集完成后则显示“打开排查包”。ZIP 中的 `crashes/<记录名>/` 含转储、采集信息和前后日志；未完成的现场不会混入，缺失和跳过原因会在界面及 ZIP 内说明。不会复制配置文件或自动上传；完整转储可能含个人数据且体积较大，请仅分享给可信的排查人员。原有“导出诊断”仍可单独使用。

- `client.log`：带时间的连接状态、进程识别、helper 退出结果、IPC、成员数量、断线原因；每 10 秒记录收发和延迟统计。
- `injector.log`：目标检查、DLL 加载及初始化返回码（返回 2 表示该进程已初始化过，需重开游戏）。
- `hook.log`：Steam 接口、回调入口、IPC 初始化/异常、回调执行次数和入口补装次数；不收集或调用游戏注册的回调对象。

每份日志上限 2 MB，滚动保留一份同名前缀的 `.previous.log`。日志不包含组码、token、SteamID 或游戏包内容；关掉工具后仍会保留。排障时发送这三个日志及存在的 previous 文件即可，不要发送 `settings.json`。日志写入失败会显示在日志窗口中；旧版本运行期间的记录无法补回。

Relay 的 stderr 由服务器上的 systemd journal 收集。它只记录生命周期事件，以及每 10 秒一次的在线数、已绑定游戏数、TCP/UDP 投递数、拒绝数和队列字节等累计汇总；不会逐包记录，也不会写入组码、token、显示名、SteamID、IP 或 payload。查看、导出和保留策略核查命令见 [服务器部署说明](docs/server-ai-handoff.md)；不要为排障擅自调整全局 `journald` 配置。

成员退出或重开游戏时，Relay 会丢弃仍发往旧目标的 TCP/UDP 数据，避免发送方因残留包而退出联机。汇总中的 `target_unavailable` 表示同组目标当前不可用，`target_epoch_expired` 表示目标游戏实例已改变；发送方身份或实例不匹配仍记录为 `packet source or epoch is invalid` 并拒绝。此修复需要更新 Relay 才会生效，仅更新客户端不能修复旧 Relay 的连带断线；它也不保证游戏在房主退出后能够继续当前对局。

## 开发者打包

### 公开发布客户端更新

源码仓库与发行仓库分开；公开发行地址固定为 [NetBurrow-Releases](https://github.com/stmluyuer/NetBurrow-Releases)。在 GitHub 创建该公开仓库并启用 Issues，只放面向用户的说明和发行包，不复制源码或私有仓库历史。首次支持更新检查的客户端仍需朋友手动下载一次。

准备 UTF-8 更新说明文件（非空、最多 12000 个字符），调用现有客户端打包入口：

```powershell
.\打包客户端.ps1 -ReleaseNotesPath .\更新说明.txt
```

说明文件路径相对于调用时的目录。除原 ZIP 外，脚本会生成 `.local\dist\updates\<版本>\latest.json`，并打印本次应上传的两个文件；不传 `-ReleaseNotesPath` 时普通打包行为不变。说明参数会在构建和版本递增前校验。自动化仍可加 `-NonInteractive`；重复打包或失败后重试可加 `-KeepVersion`。

1. 在发行仓库新建标签为 `v<版本>` 的 Draft Release，填写该版本说明。
2. 只上传 `NetBurrow-<版本>-win-x64.zip` 和该版本目录内的 `latest.json`；核对标签、ZIP、清单和程序版本一致。
3. 附件齐全后发布为正式版并标记 Latest。不要把测试包设为最新正式版。
4. 未登录访问 [更新清单](https://github.com/stmluyuer/NetBurrow-Releases/releases/latest/download/latest.json) 与对应 ZIP，确认可下载，再用旧版客户端检查。

客户端读取公开 JSON，按数字比较版本；更新说明按纯文本显示。下载链接固定指向所显示版本的 ZIP。请求使用 Windows 系统 HTTPS 和代理设置，不需要 GitHub 令牌，不上传组码或配置。更新源不可达或尚无 `latest.json` 时会显示检查失败；可以手动进入发布页。本期不验证 ZIP 签名、不自动安装，也不检查 Relay 协议兼容性；需要同时更新 Relay 时须在发布说明中明确说明。

**不要公开上传 `*-relay-source.zip` 或整个 `.local\dist`。** 通用打包脚本会生成含源码的 Relay 包；公开发行只选上述客户端 ZIP 与清单。客户端 ZIP 不包含 `LICENSES`。发布步骤由用户执行，打包脚本不会创建仓库、上传或发布。

### 常规打包

日常只打包客户端：右键仓库根目录的 `打包客户端.ps1`，选择“使用 PowerShell 运行”。脚本自动构建 x64 客户端与 32 位注入器/DLL，生成 `.local\dist\NetBurrow-<版本>-win-x64.zip`；成功后打开产物目录，窗口会保留结果，按回车关闭。默认每次打包将根 Cargo.toml 的修订号加 1（例如 0.1.0 → 0.1.1），同步 Cargo.lock，保留其他版本的 ZIP。

如果系统阻止右键运行，可在仓库根目录执行以下命令（仅对本次进程放行脚本）：

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\打包客户端.ps1
```

自动化调用可添加 `-NonInteractive`，关闭等待回车和打开目录；成功返回退出码 0，失败返回 1。脚本依赖本仓库已准备好的 `.local` Rust 工具链、离线依赖及 MSVC 构建环境，不会自动安装环境。

版本只在准备分发时递增，普通编辑或 `cargo build` 不改版本。修复和界面小调整递增修订号；新增完整功能时指定次版本（例如 `0.2.0`）；准备正式发布时指定 `1.0.0`。界面、诊断报告、启动日志及 Relay 源码包统一读取根配置版本。

```powershell
# 新功能：指定版本（不能低于当前版本）
.\打包客户端.ps1 -Version 0.2.0
# 重复打包或失败后重试：保留当前版本
.\打包客户端.ps1 -KeepVersion
```

失败后已递增的版本会保留，使用 `-KeepVersion` 重试可避免再次递增。保留版本会替换该版本的 ZIP，仅用于未发布的包；已经发给别人的内容有变化时，应使用新版本。

需要同时生成客户端包与 Relay 源码包时，在仓库根目录运行（同样支持 `-Version` 和 `-KeepVersion`）：

```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\package.ps1
```

项目不固定 Rust 版本，所选工具链需支持 Rust 2024 edition 并满足锁定依赖的最低版本要求。脚本通过 `rustup` 使用仓库 `.local` 中已配置的默认工具链，需预先安装 x64 和 i686 Windows MSVC target；离线构建桌面程序与 helper/DLL，输出到 `.local\dist`：

- `NetBurrow-<版本>-win-x64.zip`
- `NetBurrow-<版本>-relay-source.zip`

`scripts\package.ps1 -SkipBuild` 仅重新压缩已记录的构建产物，自动保留版本；版本或二进制文件与记录不符时会拒绝打包，需改用 `-KeepVersion` 重建。首次使用必须正常构建一次。

客户端包和 Relay 源码包均不生成或包含 `LICENSES`；开源时另行整理许可证材料。打包脚本不部署 Relay、不访问 VPS，也不包含 `.local`、研究资料、日志或真实配置。
